# PART 1 — PRODUCT DEFINITION

## 1.1 Product identity

Name: TraceForge AI

Primary module: ContractGuard

Tagline: From Bug Report to Verified Fix

Category: Developer Productivity / Automated Debugging / Regression Testing

Primary users:
- Full-stack developers
- Backend developers

- QA engineers
- Software maintenance teams
- Technical leads

## 1.2 Problem statement

Modern full-stack applications often suffer from API contract drift: their frontend implementations, backend endpoints, automated tests and technical documentation gradually become inconsistent.

Diagnosing these inconsistencies typically requires developers to inspect several parts of a codebase, manually reconstruct the intended behavior, reproduce failures, identify the root cause, coordinate changes and write regression tests.

This fragmented workflow creates unnecessary investigation effort, increases rework and makes it difficult to demonstrate that a correction resolves the complete problem.

TraceForge AI addresses this specific debugging and regression-testing workflow.

## 1.3 Proposed solution

Build a developer workflow application that coordinates:

1. Bug intake
2. Project and documentation analysis
3. Reproduction of the reported issue
4. Parallel investigation
5. Evidence-backed root-cause identification
6. Proposed correction
7. Human approval
8. IBM Bob-assisted implementation
9. Automated regression testing
10. Final verification and reporting
11. Measured workflow outcomes

The developer must be able to trace a problem from its original requirement to the final test results.

## 1.4 Primary innovation

Implement a Contract Evidence Graph.

Each investigation must establish traceable relationships between:

- Documented API requirement
- Relevant frontend implementation
- Relevant backend implementation
- Observable failure
- Reproduction test
- Identified root cause
- Proposed correction
- Approved code changes
- Regression tests
- Final verification

This evidence graph is the application's distinguishing feature.

Unlike a generic chatbot, TraceForge AI organizes a complete engineering workflow with reproducible tests, recorded decisions and inspectable evidence.

## 1.5 MVP boundary

The hackathon prototype must support one bundled sample project and one complete investigation scenario.

Build this workflow completely before supporting arbitrary repositories, additional AI services, advanced authentication or integrations with external issue trackers.

Implement production-quality foundations for the delivered features. Do not describe unfinished features as production-ready.

# PART 3 — SYSTEM ARCHITECTURE

## 3.1 Architectural boundaries

Divide the system into four components.

A. ContractGuard frontend

Provides investigation creation, workflow monitoring, artifact inspection, approval, verification and reporting.

B. ContractGuard Rust backend

Owns workflow state, storage, artifact validation, filesystem isolation, controlled test execution and report generation.

C. IBM Bob IDE

Performs actual project understanding, independent investigations, code modifications, regression-test creation and code review.

D. UploadLab sample application

A separate full-stack project containing deliberately introduced API contract defects.

## 3.2 IBM Bob integration

Do not assume that IBM Bob offers an externally callable runtime API.

The primary integration must use an explicit local artifact handoff.

Workflow:

1. ContractGuard creates an investigation.
2. The Rust backend creates an isolated project workspace.
3. ContractGuard generates a task-specific Bob prompt.
4. The developer opens the workspace in IBM Bob.
5. Bob reads and investigates the actual project.
6. Bob writes validated structured artifacts into the assigned run directory.
7. The developer selects Sync Results in ContractGuard.
8. The Rust backend imports and validates Bob's artifacts.
9. ContractGuard presents the findings and approval controls.
10. After approval, ContractGuard produces the implementation prompt.
11. Bob implements the correction in the isolated workspace.
12. ContractGuard independently executes the verification suite.
13. The application generates an evidence-backed final report.

Do not represent local process activity as IBM Bob activity.

Do not claim that the dashboard directly controls Bob unless an actual supported integration has been built and tested.

## 3.3 Deployment modes

Support two distinct modes.

LOCAL_WORKSPACE_MODE:

PUBLIC_DEMO_MODE:

## 4.3 Expected application behavior

UploadLab is a simple multiple-file upload application.

The user selects one or more files and uploads them through a React interface.

The backend validates each file and returns a structured result.

The documented contract is:

POST /api/upload

Content-Type:
multipart/form-data

Required field:
files

Supported file formats for the demonstration:
.txt
.png

Maximum individual file size:
5 MB

Maximum combined request size:
10 MB

Successful HTTP response:
200 OK

Example successful response:

{
  "uploaded": [
    {
      "filename": "document.txt",
      "size_bytes": 1024,
      "status": "accepted"
    },
    {
      "filename": "diagram.png",
      "size_bytes": 2048,
      "status": "accepted"
    }
  ],
  "count": 2
}

Expected behavior:
- Support one or more files.
- Reject empty requests.
- Reject unsupported extensions.
- Enforce size limits.
- Return a consistent response schema.
- Return a result for every accepted file.
- Do not silently ignore additional files.

Document how the API handles partial validation failures.

For this prototype, reject the complete request if any selected file is invalid.

Make the tests reflect this documented behavior.

## 4.4 Introduce deliberate defects

Create an immutable broken fixture containing two real bugs.

BUG-001: FRONTEND CONTRACT MISMATCH

The documented field name is "files".

The frontend sends the files using an incorrect multipart field name.

BUG-002: BACKEND PROCESSING DEFECT

The backend processes only the first file despite the documented requirement to process multiple files.

These bugs must produce observable failures.

Do not make the baseline tests pass by weakening their assertions.

Do not make the final tests pass by simply updating the documentation to match broken behavior.

## 12.4 Post-fix behavior

- No unresolved targeted regression failures.
